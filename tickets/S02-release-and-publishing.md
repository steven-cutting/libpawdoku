# S02: Spike: release and publishing, cargo-release or release-plz, crates.io, lifting publish = false

## Context

Every crate is `publish = false` through `[workspace.package]` (CONVENTIONS.md §1
decision 3, T00 step 4) until this spike decides the release process and settles the
crates.io name. §12 assigns one claim here: that `pawdoku` is free on crates.io; §13
says why it matters early: a rename later touches every page, the manifest, the
CHANGELOG and G's future import. §10 reserves a `release.yml` for the workflow this
spike designs, because it needs `contents: write` and `id-token: write` (crates.io
trusted publishing through OIDC, §11 "Credentials") and so never shares `ci.yml`.

Facts to start from, each verified at execution against the tool's current
documentation or `pixi search` (versions on 2026-09-23: cargo-release 1.1.6, release-plz
0.3.169, cargo-semver-checks 0.50.0):

- The house CHANGELOG is Keep a Changelog 1.1.0 prose (G's `CHANGELOG.md` at
  `78d03cdf` lines 5-6; T10 writes this one the same way) and house commit subjects are
  short imperative prose, not conventional commits (B's history: "Add the composite
  action that sets up the game toolchain"). cargo-release does not read commits: it
  bumps versions, runs `pre-release-replacements` over named files (the `[Unreleased]`
  heading becomes `[x.y.z] - date` and the link definition is rewritten), tags and
  publishes. release-plz derives the version and the changelog from conventional
  commits through git-cliff, so on this history it would write a changelog nobody
  wrote and a bump it cannot justify; git-cliff alone has the same dependency.
- cargo-semver-checks compares the public API against the last tagged or published
  version, so it has nothing to compare until the first tag; before 1.0 a breaking
  change is a minor bump, so it runs outside `check`'s `needs` first and joins them at
  1.0 (CONVENTIONS.md §10).
- Trusted publishing: crates.io accepts a GitHub Actions OIDC token for a crate whose
  owner has named the repository and workflow as a trusted publisher; verify whether
  that can be configured before the first version exists, or whether the first publish
  uses a maintainer token that is then revoked.
- The binding crates (S04) ship to other registries (a binary release, PyPI, npm).
  Lockstep (one version, one tag) is simple and wasteful for a one-crate change;
  independent versions need a tag per crate (`pawdoku-v0.2.0`, `pawdoku-wasm-v0.1.3`)
  and per-package configuration; `shared-version = true` in `release.toml` is the
  lockstep switch.

Read first: CONVENTIONS.md §1 decision 3, §10 (last paragraph), §11, §12, §13;
`Cargo.toml` and `crates/pawdoku/Cargo.toml` as T02 left them (`publish.workspace =
true`, `rust-version`, `readme`, `[package.metadata.docs.rs]`); `CHANGELOG.md` as T10
wrote it; `docs/decisions/0007-dependency-policy.md`; B's `README.md` at `6c5c07f6`
lines 250-291, the house versioning rules and the precedent for MAJOR, MINOR and PATCH.

## Goal

A recommendation for how the first and every later release of `crates/pawdoku` is cut,
with evidence in the hand-back notes, and a drafted build ticket that implements it.
Nothing is tagged, published, configured on crates.io or installed into the
repository. The starting recommendation: **cargo-release**, with
`pre-release-replacements` on the CHANGELOG heading and link definition,
`shared-version` off until a second crate exists (then decided with S04), tag
`v{{version}}` for the core, the bump and tag made on a maintainer's machine, and
`release.yml` publishing on the tag through trusted publishing.

| Option | Reads commits | Changelog | Tag and publish | Fits the house | Cost |
| --- | --- | --- | --- | --- | --- |
| cargo-release | no | replacements over prose the maintainer wrote | tags, pushes, publishes, or stops before any step | yes: imperative commits, Keep a Changelog | `release.toml`, a pixi dependency or a `tools.txt` line (T00 follow-up), one workflow |
| release-plz | yes, conventional | generated by git-cliff from commit types | a release pull request, publish on merge | no: house commits carry no type prefix | the same files plus a commit convention the house lacks |
| git-cliff alone | yes | generated | neither | no, for the same reason | a config for a changelog already written by hand |
| By hand | no | by hand | `git tag -a`, `cargo publish` | yes, at zero cost | a tag without a bump, a publish without a tag |

## Non-goals

- Publishing, creating a crates.io account or owner, reserving a name, tagging, or
  lifting `publish = false` (the follow-up does it on `main` once the name is settled
  and the workflow exists).
- The binding crates' release mechanics (maturin's wheel matrix, wasm-pack and npm
  provenance, cargo-dist): S04 names them; this spike decides only lockstep versus
  independent versions.
- A 1.0 date or an API stability promise.

## Steps

1. Create the worktree on `ticket/s02-release-and-publishing` from `main` after T11
   has merged (README.md "How to pick up a ticket").

2. The name, read-only:

   ```sh
   cargo search pawdoku --limit 5
   curl -sS -A 'libpawdoku-S02 (github.com/steven-cutting/libpawdoku)' https://crates.io/api/v1/crates/pawdoku | head -c 400
   ```

   crates.io refuses requests without a `User-Agent`; do not use `gh api` for a host
   that is not GitHub, because gh may attach its token. No `pawdoku =` line from
   `cargo search` and a not-found body from the API mean the name is free. Check
   `pawdoku-cli`, `pawdoku-py` and `pawdoku-wasm` for S04 too and record all four. If
   `pawdoku` is taken, list candidates (`libpawdoku`, `pawdoku-engine`) and stop at the
   recommendation: the rename is the maintainer's.

3. Verify the trusted-publishing sequence against crates.io's current documentation:
   whether a trusted publisher can be configured on a crate with no version yet; if
   not, the first publish is a token publish from the maintainer's machine and the
   token is revoked after; the `id-token: write` job shape and the action that
   exchanges the token, with its version and the SHA lookup of CONVENTIONS.md §10.

4. Verify cargo-release's behaviour on this tree, dry-run only, from a scratch install
   (`pixi search cargo-release` first; if conda-forge carries it, `pixi exec --spec
   'cargo-release==1.1.6' cargo-release ...` in place of the line below, otherwise
   `cargo binstall cargo-release@1.1.6 --root <scratch>` with the environment's
   cargo-binstall; nothing under `.tools/` or `.pixi/`):

   ```sh
   <scratch>/bin/cargo-release release --workspace --dry-run patch
   ```

   Record whether it refuses a `publish = false` crate, what `release.toml` needs
   (`pre-release-replacements` on `CHANGELOG.md` for the heading and the link
   definition, `tag-name`, `pre-release-commit-message`, `push = false` and
   `publish = false` for the local step), and that the tree is unchanged after.

5. Verify cargo-semver-checks' baseline requirement (a tag or a published version),
   whether 0.50 needs a nightly for rustdoc JSON, and the job shape
   (`cargo semver-checks --baseline-rev <last tag>`, outside `check`'s `needs` until 1.0).

6. Decide lockstep versus independent versions for the four crates, with S04's crate
   list in view: G will pin an npm version of `pawdoku-wasm`, and a core-only change
   should not force a PyPI release.

7. Draft the follow-up build ticket: id `T13`, files (`release.toml`,
   `.github/workflows/release.yml`, the cargo-release pin as a pixi dependency in
   `pyproject.toml` when conda-forge carries it (`pixi search cargo-release`) and
   otherwise a `tools.txt` line, either a T00 follow-up, `Cargo.toml` lifting `publish`
   for `crates/pawdoku` only, the binding crates keeping
   `publish = false` in their own manifests, a "Cut a release" section in
   `docs/operations/maintenance.md`, the first `[0.1.0]` heading in `CHANGELOG.md`),
   the authorisation steps (crates.io account and trusted publisher, the tag, the
   push), and the proof (a `0.1.0` publish whose docs.rs build is green).

8. Set `status: done` and commit on the ticket branch. Stop before pushing.

## Open points

- Whether the maintainer wants the bump and tag made locally (the workflow publishing
  on the tag) or a release pull request opened by a workflow, which is release-plz's
  shape and needs the commit convention.
- Whether `rust-version` stays in lockstep with `rust-toolchain.toml` after the first
  publish (CONVENTIONS.md §2 says "until the crate is first published"); a published
  `rust-version` is a promise to consumers and should move slower than the pin.
